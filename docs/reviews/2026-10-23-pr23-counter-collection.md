# PR #23 柜台领取与快递授权对齐

## 业务规则

失主可以在批准后先授权快递，再选择自己到场领取。收到 `claim.handed_over` 且 `mode=counter` 时，Delivery 必须将尚未取件的运单从 `awaiting_pickup` 转为 `cancelled`，原因为 `collected_at_counter`。不能继续保留可供快递履约的活动运单。

取消运单、递增版本、写入历史、写入 `delivery.status_changed` outbox 和 inbox 去重记录都处于消费事务中。现有伙伴详情接口按终态隐藏地址，活动运单列表也会排除这笔运单。失主仍可查看自己的历史资料。重复的同一事件或不同事件 ID 的同一柜台领取不会重复生成状态变更。

没有快递授权的柜台领取正常结束；已经进入快递运输状态却又收到柜台领取，作为状态冲突保留消息并交由重试和 DLQ 处理，不覆盖运输记录。事件必须包含 mode；缺失时按共享契约拒绝，不确认消息。

## 并发与成员对齐

创建授权与 Claim 关闭事件都获取相同认领 ID 的事务级 advisory lock（API 对 ClaimApproval 仍然只有读取权限），防止关闭事件已处理、另一事务仍按旧批准状态创建新运单。事件还必须与运单的场馆、认领、物品和失主一致。

前端无需新增接口；已授权快递后到场领取仍使用 counter 扫码。伙伴应按终态停止派件，处理取消事件并停止缓存或使用收货地址。异步事件生效前可能存在短暂延迟，已发送给伙伴的地址无法通过 API 物理收回。

回归测试覆盖纯业务规则，以及真实 PostgreSQL 下的授权、柜台领取、重放、地址隐藏、活动列表过滤、拒绝后续运输更新、历史和 outbox 唯一性。
